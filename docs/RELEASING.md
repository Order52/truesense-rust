# Releasing

One command prepares a release; pushing the tag publishes it. Nothing is built or uploaded by hand, and nothing in the process needs Python or Go: the release tool is a shell script, the program is one static Rust binary.

```
# 1. write what changed under "## Unreleased" in RELEASE_NOTES.md (as you merge changes)
# 2. prepare: bump every version, retitle the notes, refresh Cargo.lock, run the gate (make ci and the shell checks and tests), commit, tag
tools/release.sh prepare 0.5.0 --title "short title of the release"
# 3. publish: the tag push starts .github/workflows/release.yml
git push origin HEAD v0.5.0          # or:  tools/release.sh prepare ... --push
```
`prepare` refuses a dirty tree, a version that is not newer, an existing tag, empty "Unreleased" notes, or a release without a title. `--dry-run` shows what it would do; `--no-gate` skips the gate (CI runs it again anyway). The other commands: `tools/release.sh check [--tag vX.Y.Z]` (do the version numbers, notes and tag agree?; `make release-check` runs it), `version`, and `notes X.Y.Z` (the GitHub release text).

The version lives in the workspace `Cargo.toml` (`[workspace.package] version`, compiled into the program as `CARGO_PKG_VERSION`), and `tools/release.sh` knows every other place that must say the same: `Cargo.lock` (the workspace crates' entries; `prepare` refreshes it with `cargo update --workspace --offline`, which moves no dependency), `docs/INSTALL.md`, the kernel module (`dkms.conf` and `truesense_wmi.c`), `tools/aur-publish.sh`, `tools/get.sh` and both PKGBUILDs (`pkgver`; the DKMS directory name in the packages is read from `dkms.conf`, not repeated). `ts-qt` has no row of its own: it takes `version.workspace = true`, so `truesense-qt --version` prints the same number (the installer and the CI checks compare it with the tree's version). The table is at the top of the script; `prepare` rewrites only those places, so a stray mention of the same digits elsewhere is left alone.

## What the program's updater needs from a release
The updater inside the program (`truesense update apply`, the window's Settings, Update) downloads `truesense-X.Y.Z.tar.gz`, verifies it against `SHA256SUMS`, unpacks it and runs its `tools/install.sh` as root. It accepts the archive only if the top folder holds `tools/install.sh`, `kernel/truesense-wmi/truesense_wmi.c` and a `Cargo.toml` whose **first standalone `version = "x.y.z"` line equals the tag** (`ts-system::update::Layout::rust_edition`). This is kept true three times: the root `Cargo.toml` must keep the workspace version as the first `version = "..."` in the file (nothing with that spelling above `[workspace.package]`; `rust-version` does not count), `tools/release.sh check` fails otherwise, and `tools/ci/check-bundle.sh` checks the same inside the finished bundle.

## What the pipeline does (release.yml)
1. **verify**: the tag, `Cargo.toml`, `Cargo.lock`, the kernel module, DKMS, both PKGBUILDs, `get.sh`, `docs/INSTALL.md` and the release notes all agree (`tools/release.sh check --tag vX.Y.Z`); the tagged commit is on `main`; `Cargo.toml` and `Cargo.lock` are committed; `make ci` (rustfmt, clippy with warnings as errors, every test), the shell tests and a module build pass.
2. **build**: the static `x86_64-unknown-linux-musl` program and the **bundle** `truesense-X.Y.Z.tar.gz`, built by `tools/ci/build-bundle.sh`, which builds the program **twice, from two fresh copies of the archived tree in two different directories, and stops unless the two are byte-identical**, then checked by `tools/ci/check-bundle.sh` (complete, the program inside runs and says `truesense X.Y.Z`, really static, owned by root, no kernel build leftovers, the updater's `Cargo.toml` rule). The release notes are cut from `RELEASE_NOTES.md`, a CycloneDX **SBOM** is generated by `tools/ci/sbom.sh`, and `truesense-X.Y.Z.build-env.txt` records the compiler and the commit.
3. **package-arch**: the Arch package, built with `makepkg` as an unprivileged user in a clean Arch container (it builds the static program and the Qt window with cargo; makedepends `rust gcc qt6-base qt6-declarative qt6-svg qt6-tools`). The window is then taken out of the package into **`truesense-qt-X.Y.Z-linux-x86_64.tar.gz`** (`truesense-qt-X.Y.Z/bin/truesense-qt` and `BUILT-WITH.txt`, which records the Qt version and the libraries it needs), after checking that it says `truesense-qt X.Y.Z`. One build, two ways to get it. It is deliberately **not** part of the reproducible bundle: the bundle stays the source tree plus the static musl program, byte for byte; the Qt app is dynamic, so its bytes depend on the Qt and glibc of the build machine and a reproducibility claim would be false.
4. **publish**: `SHA256SUMS` over the bundle, the package, the Qt window tarball, the SBOM and the build-environment file, a signed **build provenance attestation** for every file including `SHA256SUMS` (Sigstore, no keys to keep), then the GitHub release with all of it and the notes. It finally runs `tools/get.sh` against the published release exactly as a user would, with the checksum **and** the attestation check on.
5. **aur** (only if the `AUR_SSH_PRIVATE_KEY` secret is set): pushes the PKGBUILD (it refuses a tag whose source does not declare the version). Otherwise run `tools/aur-publish.sh X.Y.Z` yourself.

Re-publish an existing tag, or rehearse without publishing: Actions, Release, Run workflow, give the tag, leave "dry run" on.

## How the build is made reproducible
`tools/ci/build-binary.sh` is the one place that builds the released program (the Makefile's `make build` and the bundle script both call it):
- `--remap-path-prefix` renames the source tree, `CARGO_HOME` and `RUSTUP_HOME` in everything the compiler embeds, so the directory of the checkout never reaches the binary;
- `SOURCE_DATE_EPOCH` (the commit time) gives the build date compiled in (`TRUESENSE_BUILD_DATE`), and `TRUESENSE_COMMIT` the short commit; the clock is never read;
- `--locked` makes `Cargo.lock` decide every dependency version; `CARGO_INCREMENTAL=0`, `TZ=UTC`, `LC_ALL=C`;
- the musl target links one static-pie program with no libc to match. The repository's `rust-toolchain.toml` names `stable`, so **the compiler version matters for byte-for-byte rebuilds**: it is in `truesense-X.Y.Z.build-env.txt`; check out the tag, use that toolchain, run `tools/ci/build-bundle.sh X.Y.Z /tmp/out`, and `sha256sum` gives the hash of the release.

## What a release contains
| File | What it is |
|---|---|
| `truesense-X.Y.Z.tar.gz` | the **bundle**: everything `git archive` of the tag has (minus any kernel build leftovers that were committed by mistake), plus the prebuilt static program `bin/truesense`. Top directory `truesense-X.Y.Z/`. `tools/get.sh` downloads it and runs its `tools/install.sh`, which installs `bin/truesense` (and refuses one whose version differs from the source tree) |
| `truesense-X.Y.Z-1-x86_64.pkg.tar.zst` | the Arch package (the static program, the Qt window, the units, the module sources) |
| `truesense-qt-X.Y.Z-linux-x86_64.tar.gz` | the prebuilt **Qt window**: `truesense-qt-X.Y.Z/bin/truesense-qt`, built on Arch Linux against its current Qt 6 (see `BUILT-WITH.txt` inside). Optional: `tools/get.sh` adds it to the bundle after checking it, `tools/install.sh` installs it when it runs on that machine and leaves it out otherwise. It needs Qt 6 and a glibc at least as new as the build machine's; on other systems build it from source (`make qt-release`) |
| `truesense-X.Y.Z.sbom.cdx.json` | the SBOM: the Rust crates and versions compiled into the program, with licences and source hashes |
| `truesense-X.Y.Z.build-env.txt` | the compiler, linker and commit the release was built with |
| `SHA256SUMS` | checksums of the five files above |

## Verifying a download
```
sha256sum -c --ignore-missing SHA256SUMS                      # the file you downloaded is the one that was published
gh attestation verify truesense-X.Y.Z.tar.gz --repo Order52/truesense   # and CI built it from this repository (any file, SHA256SUMS included)
```
The one-line installer does the first check always and the second when you set `TRUESENSE_VERIFY_ATTESTATION=1` (it needs the GitHub CLI). The SBOM is a standard CycloneDX file: feed it to any vulnerability scanner (`grype sbom:truesense-X.Y.Z.sbom.cdx.json`).

## Everyday CI (ci.yml)
Every push and pull request:
- **Static checks**: `Cargo.lock` tracked and resolving, shellcheck, actionlint, the version consistency check (`tools/release.sh check`), systemd unit verification (with a hardening-score ratchet that may only improve), desktop entries, and the shell tests (`tools/shelltest/run.sh`: the installer, `get.sh`, `release.sh`, the packaging and `check-bundle.sh`, with fake os-release files, fake DMI data, fake programs and a local fake GitHub; nothing is installed).
- **Rust**: `make ci` (rustfmt, clippy with `-D warnings`, `cargo test --workspace`). It does not build the Qt app (`ts-qt` is not a default workspace member), so it needs no Qt.
- **Qt window** (`qt` job, `continue-on-error`, **not in `CI passed` yet**): `make qt-ci` (rustfmt, clippy, the end-to-end tests and the QML component tests, all with `QT_QPA_PLATFORM=offscreen`) in an Arch container with the Qt 6 packages. It is not blocking because it has been verified on a development machine and not yet on GitHub's runners; add `qt` to `ci-ok`'s `needs` once it has been green for a while.
- **Build**: the release bundle is built (the program twice, compared) and checked exactly as the release does it, and the SBOM script runs.
- **Dependency advisories** (`cargo audit`, pinned version): reported but **not blocking yet**, so that a new advisory cannot stop an unrelated pull request; make it required in `ci-ok` once the first report is clean.
- **Kernel module** against the headers of Arch (linux and linux-lts), Ubuntu 22.04 and 24.04, Debian and Fedora; **installer** (`tools/install.sh --check`) on Arch, Ubuntu, Debian, Fedora and openSUSE (these containers have no Rust and no Python, and the check fails if the installer asks for either); the **Arch package**, whose checks now include the Qt window (it says the version, links Qt 6, the package depends on `qt6-base`, `qt6-declarative` and `qt6-svg`, the desktop entry has its page shortcuts, the attribution texts are shipped).

`CI passed` is the single check to require in branch protection. **Kernel watch** (kernels.yml) rebuilds the module against the newest kernels every Monday and opens one issue when a kernel breaks it. **CodeQL** scans Rust and C weekly and on pull requests. Dependabot keeps the actions and the Cargo dependencies current. Every third-party action is pinned to a full commit SHA; the Rust toolchain is installed with `rustup`, which the runners carry, so no action is involved.

Run the same gates locally: `make ci` (rustfmt, clippy, tests), `make qt-ci` (the Qt app; needs Qt 6 and its development files), `make static-ci` (version table, actionlint if installed, units, shell checks, shell tests), `make build` (the release program), `make audit` (if `cargo-audit` is installed).

## One-time repository settings (Settings in GitHub)
- Branch protection on `main`: require the `CI passed` check and a linear history.
- Actions, General: workflow permissions "Read repository contents" (the workflows ask for more only where they need it).
- For AUR publishing: add the `AUR_SSH_PRIVATE_KEY` secret (an SSH key registered on the AUR account that owns the package).
